# 지표 SQL 구현 노트

`queries/metrics/*.sql`을 만들면서 가이드의 KQL과 다르게 정한 부분이다. 가이드와 결과가 다르게 나올 수 있는 곳만 적는다. 아침에 검토해서 가이드 쪽을 고칠지 SQL 쪽을 되돌릴지 정한다.

## 정의를 바꾼 곳

| 지점 | 가이드 | SQL | 이유 |
| --- | --- | --- | --- |
| 직전 호출(`PrevIn` 등) | 턴 안 순번(`CallIdx`)의 직전 호출 | 같은 **에이전트 실행**(`OperationId` + `OwnerSpanId`) 안의 직전 호출 | 멀티 에이전트에서 직전 호출이 다른 에이전트의 호출이면 Input 증가분(C2)과 이론 캐시량(A 공통)이 틀어진다. 단일 에이전트 앱에서는 가이드와 같다 |
| A 공통 이론 캐시량 | 턴 첫 호출만 `Cacheable(S_a)` | **에이전트 실행의 첫 호출**마다 그 에이전트의 `Cacheable(S_a)` | 하위 에이전트의 첫 호출은 자기 prefix로 시작한다 |
| D1 꼬리 턴 | `N >= p95` | 호출 수 **상위 (1 − tail_pct) 순위**의 턴 (동률은 비용이 큰 순) | 호출 수가 정수라 `>= p95`로 자르면 동률 때문에 상위 5%보다 훨씬 많은 턴이 꼬리로 잡힌다(합성 데이터에서 36%). CLAUDE.md의 "호출 수 상위 5% 턴"과 맞는다 |
| D4 위임 시 Input 전달 비율 | `(하위 첫 Input − S_sub) ÷ 상위 직전 Input` | 같은 값 `PassRatio`와, 분모에서 상위의 고정 Input을 뺀 `PassRatioVar`를 둘 다 낸다. 판정은 `PassRatioVar`에 0.8을 적용한다 | 가이드 정의는 분모에 상위의 S_parent가 들어 있어서 상위 컨텍스트를 통째로 넘겨도 1에 못 미친다. 가이드가 "비율 1이 전체 전달"이라고 한 의미는 `PassRatioVar`에서만 성립한다 |
| 에이전트 귀속 | `gen_ai.agent.name`이 없으면 루트 에이전트 | `call_owner`: 부모 span을 거슬러 올라가 가장 가까운 `invoke_agent` span의 에이전트 | 가이드가 B1·D4에서 경고한 오귀속을 막는다. 부모 사슬이 끊기면 루트로 되돌아간다 |
| 축소 이벤트(A3) | 대화 안 직전 호출 | 대화 **+ 에이전트** 안 직전 호출 | 하위 에이전트의 작은 Input을 축소로 오인하지 않는다 |
| A1 낭비 추정 | 턴 첫 호출 중 `CacheTok = 0` 전부 | **보존 시간 안** 조건(만료·쏠림 제외)의 미스만 | 만료로 인한 미스는 A5가 센다. 같은 토큰을 겹쳐 세지 않는다 |

## 가이드에 수치 기준이 없어 임시로 둔 값

`config/thresholds.csv`에서 Note에 "임시"라고 적은 항목이다. 고객 데이터를 보고 보정하거나, 가이드에 기준을 추가한다.

`cache_mid_turn`(0.7, CLAUDE.md에 이미 임시로 적혀 있음), `a3_hit_drop`, `a6_hit_drop`, `c3_low_or_dup`, `d2_serial_share`, `d3_diversity`, `e4_trunc_rate`, `f1_fail_rate`, `f2_fail_rate`, `f3_quick_rate`.

## 낭비 추정의 성격

| 원인 | 성격 | 설명 |
| --- | --- | --- |
| A1, A2, A5, A6, F1 | 계산값 | 가이드 식 그대로 |
| A3 | 상한 | 편집 지점 이전 공유 길이를 모르므로 직전 prefix 전체가 히트했어야 한다고 본다. `[C]` 비교로 줄인다 |
| A4 | 구조적 한계 | 캐시 불가 비용 전체 |
| B1 | 계산값 | 정의 문자 수 ÷ `chars_per_token`로 근사한 토큰 × 호출 수 × P_eff |
| B2, B3, B4 | 없음 | 축소 가능 토큰은 `[S]` 리뷰로 정한다. 카드를 만들지 않는다 |
| C1 | 기준선 | `c1_keep_turns`(k) 이후 초과 Input. k는 리뷰로 정한다 |
| C2, D4 | 상한 | 필요 토큰 비율(`*_needed_fraction`)이 0이면 전달·재전송된 토큰 전체를 낭비로 본다 |
| C3 | 파생 | C2의 검색 tool 재전송 비용 × 저점수·중복 문서 비율 |
| D1 | 간이식 | 꼬리 턴 비용 − 꼬리 턴 수 × 턴 비용 중앙값 |
| D2 | 상한 | 순차 연쇄 턴의 tool 호출 비용 중 (k−1)/k |
| D3 | 상한 | 짧은 출력 호출 비용 전체. 출력 다양성이 낮을 때만 |
| E1 | 상한 | 소형 모델(`e1_small_model`) 단가로 다시 계산한 차이 |
| E2 | 조건부 | 같은 모델·유형의 저수준 호출이 있어야 기준선이 생긴다 |
| E3 | 조건부 | `e3_target_tok`가 있어야 계산한다 |
| E4 | 계산값 | 잘린 호출 비용 + 후속 호출 비용 |
| F2 | 계산값 | 실패 호출 + 재요청 추정 호출 |
| F3 | 근사 | 빠른 재입력 직전 턴 비용. 실제 재질문은 `[C]` 유사도로 확인한다 |
| F4 | 계산값 | 실패 턴 비용 |

원인끼리 같은 토큰을 겹쳐 셀 수 있어 낭비 추정은 합산하지 않는다(CLAUDE.md).

## 알려진 한계

- 토큰 수를 문자 수로 근사한다(`chars_per_token`, 기본 4). 측정법 1·2로 확정하기 전의 근사다. 한국어는 문자당 토큰이 달라서 편차가 크다.
- tool span의 `ParentId`가 요청한 chat span이거나 `invoke_agent` span이라고 가정한다. 다른 구조면 `tool_runs`의 귀속이 비어 B1·B4 사용률이 틀어진다.
- 합성 데이터는 내가 심은 문제만 검증한다. 실제 텔레메트리의 모양과 다를 수 있다.
