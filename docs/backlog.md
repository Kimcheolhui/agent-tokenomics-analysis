# 백로그

진단 가이드와 보고서 템플릿을 Agent skill로 만들기 전에 정리할 일이다. 항목마다 "무엇이 되면 끝인가"를 적는다. 1번이 나머지 전부의 전제다. 2–4번과 6번은 서로 독립이고, 5번은 그것들이 끝난 뒤에 착수한다.

## 1. 데이터 추출 방식 결정 — 끝남 (2026-11-09)

CSV 스키마를 계약으로 정했다. 추출 수단 두 가지가 같은 스키마를 만들고, 쿼리 본문은 `queries/export/*.kql` 한 곳에만 있다. 스크립트가 그 파일을 읽어 실행하므로 포털 경로와 결과가 같다. 스키마는 `docs/data-contract.md`에 있다.

- 추출 단위는 집계가 아니라 행이다. LLM 호출 1건 = 1행. 집계로 내리면 p50·p95·상자 그림을 쓰는 지표(C1, C2, D1, E2, E3)를 산출할 수 없다.
- 기간은 하루 단위 파일로 쪼갠다. 기간을 미리 정하지 않아도 되고, 행 수 한계에 걸리지 않으며, 실패한 날만 다시 뽑는다.
- 원문은 해시와 길이만 내린다. 증거용 원문은 SpanId를 특정한 뒤 2차로 받는다.
- 로컬 산출은 DuckDB로 한다. `queries/views.sql`이 가이드의 "공통 쿼리 정의"에 1:1로 대응한다.
- 25개 원인의 텔레메트리 지표가 기본 추출만으로 모두 산출된다. 원인별 필요 파일은 계약 문서의 표에 있다.

검증 상태: `views.sql`은 합성 CSV로 실행해 확인했다. 검증 중에 하위 에이전트 오귀속(가이드 B1·D4의 주의사항)을 막는 `call_owner` 뷰를 추가했다. **추출 KQL 9개는 실제 Log Analytics에서 실행해 보지 않았다.** `AppGenAIContent` 컬럼명과 `AppRequests` union 동작을 고객 환경에서 확인해야 한다.

## 2. REPORT 객체 스키마 분리

지금 `REPORT` 필드 설명은 보고서 HTML 맨 아래 `<details>`의 산문과 CLAUDE.md 요약에만 있다. Agent가 값을 채우려면 필수 키를 기계가 읽을 형태로 봐야 한다.

- `meta`, `categories`, `symptoms`, `causes`의 필드와 타입을 정의한다.
- 차트 type 9종(`hbar`, `stackbar`, `segbar`, `columns`, `line`, `box`, `diff`, `listdiff`, `pairs`)별 필수 키와 선택 키를 정의한다.
- 열거 값을 고정한다. `verdict` 6종(해당, 후보, 비해당, 계측 부재, 판정 보류, 미점검), `status` 4종(abnormal, normal, nodata, hold), `dir` 2종(higher, lower), `fmt`.
- 각 지표가 들어갈 필드를 가이드 쪽과 연결한다. 어떤 쿼리 결과가 어느 필드로 가는지 적는다.
- **끝**: 스키마 문서가 있고, 템플릿의 예시 데이터가 그 스키마를 통과한다.

## 3. 사전 점검을 진단 절차의 게이트로 만든다 — 끝남 (2026-11-09)

가이드에 "사전 점검" 절(P1–P9)을 넣고 진단 흐름 1단계로 올렸다. 점검마다 실패했을 때 영향받는 지표를 정했다. 로컬에서는 `instrumentation`, `unpriced_calls`, `missing_sa` 뷰가 같은 점검을 한다. 턴·trace 점검 쿼리는 실제 workspace에서 실행해 보지 않았다.

원래 항목:

속성 키가 쌓이지 않으면 산출할 수 없는 지표가 있다. 지금 가이드는 이 점검을 공통 전제 안의 설명으로 두고 있어서, 건너뛰고 섹션 3으로 가도 막히지 않는다.

- 점검 항목을 목록으로 고정한다. `cache_read`·`reasoning`·`conversation.id` 키 수집 여부, 턴 1개 = trace 1개 가정, `gen_ai.response.finish_reasons`의 tool 호출 실제 값, `AppGenAIContent` 읽기 권한과 content recording 여부.
- 점검이 실패했을 때 어느 원인 항목이 `계측 부재`가 되는지 매핑한다. 지금은 A 공통·A1·A5·A6(cache_read), E1·E2·D3(reasoning), C1(conversation.id)까지만 본문에 적혀 있다.
- 점검 결과를 적는 표를 만든다. 보고서의 `verdict`와 `meta.sources`로 바로 옮길 수 있는 형태로 둔다.
- **끝**: 점검 절차가 섹션 3보다 앞에 단계로 들어가고, 실패 시 보고서에 기록하는 경로가 정해진다.

## 4. S_a 선행 의존성을 실행 순서에 명시한다 — 끝남 (2026-11-09)

가이드 진단 흐름 3단계에 S_a 측정을 넣고, "S_a를 쓰는 지점" 표로 8곳을 표시했다. 측정법 1이 텔레메트리 밖(고객 배포에 요청)이고 측정법 3이 하한 근사라 낭비 추정이 낮게 나온다는 점을 적었다.

원래 항목:

A 범주의 지표와 낭비 추정은 대부분 3-B에서 측정한 S_a를 입력으로 받는다. 가이드의 진단 흐름은 "증상 → 지표 → 판정" 3단계라서 이 순서가 드러나지 않는다.

- 실행 순서를 B 공통(S_a 측정) → A 범주로 고정한다.
- S_a를 쓰는 지점을 모두 표시한다. A 공통 지표, A1 미스율과 낭비, A2 낭비, A4 판정, A5 낭비, A6 낭비, B 공통 비중, B4 낭비로 8곳이다.
- 측정법 1(실험 호출)은 고객 배포에 직접 요청을 보내야 한다. 텔레메트리만으로는 안 되는 단계이므로 사전 준비 항목으로 따로 적는다.
- 측정법 3(턴 첫 호출 InTok 1백분위수)만 쓸 수 있는 경우의 오차를 적는다. 하한 근사여서 낭비 추정이 낮게 나온다.
- **끝**: 진단 흐름에 S_a 측정이 선행 단계로 들어가고, S_a를 쓰는 쿼리마다 그 사실이 적혀 있다.

## 5. Skill 구조 설계와 작성

가이드 본문이 1,114줄 76KB다. `SKILL.md` 하나에 넣으면 호출마다 전체가 컨텍스트에 올라간다. 토큰 최적화를 다루는 skill이 컨텍스트를 낭비하게 된다.

- `SKILL.md`에는 진단 흐름, 증상 → 후보 원인 매핑, 공통 전제, 사전 점검만 둔다.
- 문제 카탈로그는 범주별(A–F) `references/` 파일로 쪼갠다. 이상 증상에 걸린 범주만 읽는다. 범주별 분량은 A 221줄, B 143줄, C 150줄, D 143줄, E 117줄, F 135줄이다.
- 보고서 템플릿과 REPORT 스키마를 `assets/`와 `references/`로 넣는다.
- **끝**: skill을 호출해 사전 점검부터 보고서 작성까지 한 번 통과한다.

## 6. 섹션 3 지표를 로컬 SQL로 옮긴다

1번으로 기본 뷰(`queries/views.sql`)까지는 로컬로 넘어왔다. 원인별 지표 쿼리 40개는 아직 가이드 본문의 KQL로만 있다. 이 상태로는 추출한 CSV를 두고도 지표를 손으로 다시 써야 한다.

- 원인별 SQL을 `queries/metrics/`에 둔다. 파일 하나가 원인 하나에 대응한다.
- 가이드 본문의 KQL 블록을 파일 참조로 바꾼다. 코드 블록이 1,114줄 중 389줄, 76KB 중 20.6KB를 차지하므로 5번 Skill 분할에도 바로 효과가 있다.
- 번역은 기계적이다. `prev()` → `lag()`, `summarize ... by` → `GROUP BY`, `percentile` → `percentile_cont`, `row_number(1, prev(x) != x)` → `row_number() OVER (PARTITION BY x ...)`.
- 판정 기준값은 SQL에 박지 않는다. 고객 데이터를 보고 보정하는 값이라 설정으로 뺀다.
- 하위 에이전트 귀속이 필요한 지표(B1, B4, D4)는 `calls.Agent`가 아니라 `calls.OwnerAgent`를 쓴다.
- **끝**: 25개 원인의 지표를 CSV와 `queries/metrics/`만으로 산출하고, 결과를 보고서 `REPORT` 객체에 넣을 수 있다.
